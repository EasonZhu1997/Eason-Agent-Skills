# 架构图设计能力

把资料转成读者能回答三个问题的图：**有哪些组成，各自负责什么，一次业务如何完成。** 从两张参考图提炼“分层总览 + 跨层流程叠加”的表达方法；不限定为 Rokid、AIUI、四层或六步，不照搬参考图中的品牌与技术结论。

## 先选要回答的问题

- “系统是什么、产品怎么归类”：分层总览。使用 [layered-overview.svg](assets/layered-overview.svg) 作可编辑起点。
- “一次请求怎么完成、数据往哪走”：在相同分层上叠加单条业务路径。使用 [cross-layer-flow.svg](assets/cross-layer-flow.svg)。
- 同时需要两者：先总览、后流程，层级名称、组件身份和顺序保持一致。只需要一张时不强制交付两张。
- 用户要求其他配色、比例或输出格式时尊重该要求；本技能默认现代企业图表风，不自动改成蓝墨纸绘。
- 用户只要求评估、内容契约或绘图规格时，停在该交付层级，不额外生成图；只报告已完成的关系检查，不声称做过渲染验收。

布局前读 [视觉与关系规范](references/design-system.md)；需要跨层交互时再读其中“运行流程”部分。素材不足、事实冲突或技术细节未证实时，按 [内容契约与事实边界](references/content-contract.md) 处理。

## 从事实到图形

1. **建立小型内容契约。** 从用户资料/仓库/文档提取图的目的、读者、系统边界、层级、组件、职责和有方向的关系。注明确定事实、合理假设和待核实内容；只有会改变主体结构的未知才询问。
2. **先校正关系，再美化。** 按抽象层级或职责分类，而不是按看起来对称来凑层。开发支持、运行服务、物理设备属于不同视角；同层并列不代表相互依赖，垂直对齐不代表专属绑定。
3. **区分静态与动态。** 蓝色层框和卡片表达结构；橙色编号节点和带箭头线表达选中的一次业务。步骤须绑定承担它的组件或明确标注待确认；没有参与本次请求的组件保留为背景，不硬串进主线。
4. **少字但不空泛。** 卡片采用“名称 + 职责 + 必要接口/边界”两至三行，细节放图下。首次出现的专业缩写提供中文释义。字体或间距不够时减少内容、拆图，不不断缩字号。
5. **生成可编辑图。** 默认复制 SVG 样例到新的任务输出目录，替换假设示例并按内容重新排版；尽量保留可选中的矢量文字。用户需要 PPTX、PNG、PDF 或位图美术效果时，用宿主实际支持的对应能力；不要把 SVG 改扩展名冒充其他格式。没有位图渲染能力就明确只交付 SVG，不声称已经导出 PNG。
6. **实际渲染并核对。** 打开最终图检查汉字、对齐、箭头和留白；跨层图从第一个编号沿线读到最后一个，逐边与内容契约核对。若改动源文件，重新渲染后再验收。具体看 [验收清单](references/verification.md)。

模板是两份通用、假设性的边缘助手示意图，不是 Rokid 官方图，不是固定产品实现。用户可替换层数、组件数、流程步数与文案。编辑 SVG 原生形状与文字无需生成式图片；用户明确要求位图新创作或图片编辑时，使用宿主的图片生成/编辑能力，并复核每个标签和箭头。

## 输出与边界

- 交付用户要求的图形文件；默认附可编辑 SVG 和简短说明，注明关系假设及未验证内容。按需要附渲染预览，不机械增加文档数量。
- 图中应有自解释的图例或标题：静态结构与本次运行路径分别是什么；何处是设备、网关/手机、网络或云服务边界。
- 技能的创建或调用不授权修改用户其他文档、提交 Git、推送仓库、上传平台或替换线上图片。
- 分享此技能时包含整个文件夹。包内不依赖原作者电脑路径、历史截图或其他技能；图形生成/渲染需要宿主提供相应工具。
