# 视觉与关系规范

## 两张参考图提炼了什么

- 第一张用横向分层大框建立全景：左侧统一层标签，右侧组件白卡；从基础到生态形成阅读层次。
- 第二张保留相同分层，以橙色编号、连接线和跨层注释叠加一次业务过程；蓝色结构回答“是什么”，橙色路径回答“怎么运行”。
这里提炼的是方法，不保证原图中的名称、参数、芯片职责或服务部署位置当前正确。也不沿用可能把相邻步骤误连成另一条路径的线。

## 默认视觉参数

面向横屏讲解，推荐 16:9、1600 × 900 作为起点；文档窄栏可改为上下分图。以下均是设计起点，不是强制坐标。

| 元素 | 建议 |
| --- | --- |
| 画布 | 白色或极淡冷色渐变，避免装饰抢占结构信息 |
| 外边距 | 32–64 px；页脚单独留区，不能贴底裁切 |
| 主标题 | 34–42 px，深黑/深灰；一句话说清图的目的 |
| 副标题 | 18–22 px，交代范围或阅读方式 |
| 层框 | 1.5–2 px 蓝色描边，圆角 12–16 px，淡蓝底 |
| 左层标签 | 约占宽度 12%–16%，蓝底白字；层名称优先，编号次要 |
| 组件卡 | 白底、细蓝边；卡名 22–26 px，职责 18–20 px |
| 常规色 | 蓝色 #2F63E8；正文 #172033；次文字 #5F6B7A |
| 本次路径 | 橙色 #E64A19，2.5–4 px 线与清晰箭头、白字编号 |
| 图例 | 解释蓝色组成、橙色流程，以及实际使用的虚线/灰线含义 |

中文优先可用的无衬线字体，例如 PingFang SC、Noto Sans CJK SC；若缺字换字体。不要把字体文件直接打包，除非许可允许。两个模板只有系统字体回退，无联网依赖。

## 分层总览

- 层的依据统一：可以按抽象层级、职责、控制边界分，但不要一层讲硬件、一层讲时间节点，却暗示它们属于同一维度。
- 基础层默认在下，高层在上；用户已有顺序可保留，但两张相关图必须一致。不是所有系统都需要四层。
- 同层卡片可按用途分组；宽度可随信息量调整。不要为对称凭空补组件，也不要把本不相关的产品拼成一体。
- 总览无必要调用关系时可完全不画箭头。层间箭头如仅表示“能力支撑”，须在图例明确，不当作每卡到每卡的调用承诺。
- 工具、文档、社区等支持资源可以单列为支持层，但不能仅凭位置推断其处于线上请求执行链。
- 卡片只保留名称、职责和关键边界。版本、网址、型号等与图意无关时移到图下说明。

## 运行流程

在总览上叠加一条选定路径，不试图同时覆盖全部能力。

1. 固定已确定的层次和组件身份。可以为步骤腾出左侧泳道，右侧保留组件目录；标注“步骤”与“组件”，防止以为有两套服务。
2. 每步用动词短语，编号只是本次顺序。步骤所在层表达执行归属，不把“在哪配置”混成“在哪运行”。一组件可执行多步，一步也可通过注释标明协作。
3. 建立有向边清单后再布线。相邻、同层、回到起点不自动构成边；不能为了闭环美观补一条不存在的直达路径。
4. 请求与返回用不同通道布线。线尽量贴近图的走廊，不穿文字或无关卡片；跨线无法避免时使用绕行或桥接标记，不能让普通交叉看成汇合点。
5. 跨设备、手机/网关、网络、云端或信任边界时，在交接处写清“谁 → 谁，传什么”。只有资料确认时才写 BLE、HTTPS、端侧模型等具体协议/部署信息。
6. 默认画成功主线。若错误/弱网/离线分支是本图主题，使用有标签的分支和重试条件；否则写在图下，不能让六步主线变成几十条线。
7. 开发平台、调试工具、门户和社区只是背景支持时不连入实时主线。需解释开发链时另画“开发—测试—发布”视图。

橙色不能同时表示执行路径、错误和风险。颜色之外还要有编号、标签和线型，黑白查看仍能读懂。

## 可编辑模板

两个 SVG 为假设性的边缘助手，不包含官方 Logo。复制到任务目录再改，不直接覆盖包内模板。`data-step` 以及连接线的 `data-from` / `data-to` 可辅助逐边核对；它们不是自动布局引擎。改了步骤数或关系时同步修改标记、箭头、图例与说明，必要时重做布局。
