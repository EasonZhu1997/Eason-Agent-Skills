# 内容契约与事实边界

画图前根据复杂度口头或在工作稿中明确这些内容，不强迫简单任务填长问卷：

```text
图的目的 / 读者：
系统范围 / 不在范围内的内容：
层级（有顺序）及划分依据：
组件（稳定名称、归属、职责）：
关系（起点 → 终点、含义、方向）：
本次路径（可选，步骤 → 执行组件）：
设备 / 网关 / 云端等边界：
已知事实 / 假设 / 待核实：
输出比例、格式及署名要求：
```

## 优先分清的关系

- **属于**：组件在哪个层/系统内，用容器或分组表达。
- **依赖**：谁需要谁的能力，用有标签的依赖线表达。
- **数据流**：什么载荷从谁到谁，用有方向、带载荷说明的箭头表达。
- **执行顺序**：本次具体经历哪些步骤，用编号与路径表达。
- **支持**：文档、工具、社区如何帮助开发，不自动等于运行时依赖。

一根线只承担明确含义。图例没有解释的线，应补说明或删掉，而不是让读者猜。

## 不从参考图推导事实

用户给出的截图用于版式提炼时，不把其中的产品名称、重量、芯片、API、网址、协议或运营状态写入通用规则。若用户要求重画同一个真实系统，先基于其提供的完整资料；会变化的关键参数、接口或部署归属应查对应官方一手材料，并记录来源与日期。无法验证时写“资料描述”或“待核实”，不补造。

多个来源冲突时保留差异，不为了图面整齐暗中选一个。关键归属会决定主路径时问一个聚焦问题；不关键的细节移出主图，先完成确定部分。

### 假设性样例的用法

包内边缘助手示例假设：终端采集输入，运行环境整理，经网关转发至服务侧解析、处理、生成，再回到终端反馈。它只是展示跨层路径的布线方法，不代表任何品牌的真实链路。换成用户项目后，先替换这些假设，不保留“看起来合理”的旧节点。

数据流箭头不表示必然成功，也不证明已经上线、真机验证或完成提审。若需要表达验证状态，单独使用“已验证/待验证”标签并提供对应证据。
