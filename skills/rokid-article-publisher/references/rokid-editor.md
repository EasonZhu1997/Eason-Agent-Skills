# Rokid 编辑器操作与校验

本参考适用于用户已指定的 Rokid 论坛图文任务。下面记录的是已验证过的编辑方式与容易失败的环节；具体页面、按钮和工具参数以当前浏览器状态为准，不照搬旧帖子编号、选择器或账号。

## 定位目标与保存基线

从用户给出的帖子详情页核对标题与作者上下文，再打开页面提供的编辑入口。曾验证可用的路径是原帖底部“更多”菜单中的“编辑”；新版本若入口不同，用当前可见页面确定。不要根据路径规律猜测另一个帖子或静默切到新建页。

新帖模式需要确认用户确实要求创建新帖子，以及标题、板块、可见范围和其他实际必填信息。活动稿按用户指定的当前征文规则选择；普通稿不要自动套用某个活动板块。原帖编辑默认保留原有字段。遇到不能推定的必填信息时停止提交，明确指出缺哪一项。

编辑前保存只读快照到本次任务的私有临时目录，至少记录：

- 目标详情页和编辑页的对应关系、文章标题；
- 正文 HTML 或按阅读顺序提取的文本、标题、图注、代码、图片块；
- 每张现有图片的 `src`、加载状态、自然宽高、相邻图注或正文；
- 发布表单已有的板块和可见范围等字段。

快照含正文和可能带签名的资源地址，不得收入可分享技能。不要复制浏览器存储、Cookie、访问令牌或内部应用状态来“备份”。

## CUA 操作边界

先通过当前 CUA 文档支持的方式定位已有浏览器和标签页。工具重置后重新获取当前状态；不复用陈旧标签页编号或操作节点。页面读取使用可访问性树、截图、定位器和只读 DOM 信息。选择器须从已观察到的页面元素建立。

上传、粘贴、保存和发布使用普通界面动作。仅在已聚焦的编辑器中执行剪贴板粘贴；长文本全选前确认焦点确实在正文，不在标题、地址栏或整张网页。

只读 DOM 检查可读取元素的文字、`outerHTML`、图片 `complete/naturalWidth/naturalHeight` 以及 `getComputedStyle` 的实际字号、颜色、粗细。`evaluate` 不得设置 `innerHTML`、改变 DOM、分发伪造输入事件、调用隐藏的编辑器实例或站点内部 API。不要改用终端浏览器调试协议、网络请求或页面脚本绕过 UI。

## 图片原生上传

优先尝试页面原生图片按钮和文件选择器。若当前工具的文件选择器失败，而它明确支持图片剪贴板，可以写入本地原图的二进制 `image/png` 或 `image/jpeg` 项，聚焦正文后正常粘贴。不能把本地路径字符串当作已经上传的图片，也不能把图片文件名作为身份凭据：剪贴板上传后的文件名可能全部相同。

少量图片逐张上传最容易核对。批量上传时：

1. 记录上传前正文已有的图片地址集合与数量。
2. 一个批次中尽量使用宽高互不重复的原图，并控制剪贴板负载；实际容量以当前工具为准。
3. 上传后只看新增图片。完成顺序可能与输入顺序不同，用新增 URL、自然尺寸和可见图像确认源序号。
4. 同尺寸图片不能在同批中仅凭尺寸配对。平台缩放、转码或加载未完成导致无法唯一确认时，采用单张上传或明确的可视核对，不猜顺序。
5. 若本次粘贴状态不明，先检查当前新增图；不要直接重复上传整批制造重复项。

正式地址必须来自本次论坛原生上传流程。其他网站的图片热链、`data:`、`blob:`、本地路径及上传中的占位地址都不能作为最终映射。论坛可能使用不同托管域名，应以本次原生上传返回并实际加载的地址为准，不写死一个域名或端点。

图片资产读取工具可能不接受服务器返回的通用二进制 MIME。此时不能只改扩展名或 MIME 宣称已完成线上文件哈希验证；记录无法读取的限制，用本次原生上传的增量记录、自然尺寸、可见图像及位置完成能证明的核对。

## 图片位置与富文本兼容

图片数量应依据源稿的出现次数，不是媒体文件去重数量，也不是固定值。封面通常依据前后正文定位；图注在图上还是图下，以源稿为准。

图注可能有括号中的来源说明差异。可以先标准化全半角和空白、比较稳定标题前缀，但必须唯一匹配；遇到相同图注，结合前后正文和源顺序消歧。不要用含糊的全文子串替换修改正文。

当前编辑器曾出现：`<p><img ...></p>` 粘贴时丢图，而正文顶层 `<img width="100%" ...>` 保留成功。因此准备粘贴片段时，把图片与标题、段落作为同级块：

```html
<h2>示例章节</h2>
<p>保留作者现有正文。</p>
<img width="100%" src="{{IMAGE_1}}" alt="示例图" style="height:auto;max-width:100%;">
<p>图｜示例图注</p>
```

这是针对已观察编辑器的兼容形式，不代表论坛永远只接受该结构。先验证小范围粘贴的实际结果；若图片被过滤或结构变化，保留源图与快照，调整兼容 HTML 后在同一目标继续。不要把“成功粘贴文字”当作图片已保留。

替换全文编辑区只能使用从当前正文基线生成、已核对差异的片段，确保用户手工改动仍在。无法证明正文保真时，改为局部归位或先解决差异，不用较旧的 Word 正文覆盖线上新内容。

## 离线模板与映射

本节保留原有 Word / HTML 路线：`docx_inventory.py` 清单、`{{IMAGE_1}}` 和 `fill_image_map.py`。新增 MD 路线使用 `{{RK_IMAGE_0001}}`、`prepare_text.py` / `finalize_images.py`，见 [MD 图片回填](md-image-mapping.md)；两套 schema 和映射不可混用。TXT 的默认纯文本路线与 MD 富文本兼容范围见 [富文本转入](richtext.md)。

`docx_inventory.py` 仅用 Python 标准库读取 Word，输出 `manifest.json` 和 `media/`。它拒绝危险 ZIP 路径和非空输出目录，不下载外部引用。浮动图仅能按 XML 锚点顺序记录，需要可视检查；候选图注也不能自动当作最终位置。

Manifest 的核心字段如下。真正运行时图片数量从源稿得出，示例只展示结构：

```json
{
  "schema_version": 1,
  "source": {"filename": "article.docx", "sha256": "source-digest"},
  "image_occurrences": 1,
  "unique_media": 1,
  "images": [
    {
      "order": 1,
      "paragraph_index": 4,
      "relative_path": "media/image-digest.png",
      "sha256": "image-digest",
      "width": 1200,
      "height": 800,
      "caption": "图｜示例图注",
      "preceding_text": ["图前正文"],
      "following_text": ["图｜示例图注"]
    }
  ],
  "warnings": []
}
```

原生上传映射 `native-uploads.json`：

```json
{
  "schema_version": 1,
  "images": [
    {"order": 1, "url": "https://forum.example.invalid/native/image?id=example"}
  ]
}
```

示例地址不能上传或使用。实际运行须写入通过原生上传观察到的地址，并把其 origin 传给 `--allowed-origin`。若论坛确实使用多个原生托管 origin，可多次提供该参数。该参数不能用来把跨站热链伪装成原生上传。

模板中每个 occurrence 恰好对应一个 `src="{{IMAGE_序号}}"`，从 1 连续编号；允许前导零。先把这些顶层图片放在已确认的位置，再执行映射替换。助手拒绝缺漏、重复、顺序错乱、未确认域名、嵌套目标图片和可能引入其他来源的 `srcset`。现有原生图片可以保留，但它们也必须在顶层；源清单应只覆盖本次需要填充的占位图片。

全篇归位时，清单覆盖全篇所有图片 occurrence；已确认正确的原生 URL 可以直接复用，不必再次上传。只修局部图片时，可另建本次修复的子清单，将待填充图片从 1 连续编号，并在任务记录中保留它们对应的原稿序号。不要把含全篇图片的清单直接交给只有几个占位符的模板。最终仍用原稿全量清单核对“保留的现有图 + 本次修复图”，防止局部成功掩盖其他缺图。

`fill_image_map.py` 输出新的 `article.html` 和 `audit.json`，只替换对应 `src` 值，其他 HTML 字符保持原样。它不自动寻找图注、不决定图片身份、不修改文章措辞或排版，也不是 HTML 安全清洗器。它的成功不能证明站点已经保存或读者可以看到图片。

## 标题、正文与代码

先从源稿和现有正文建立结构清单，再恢复语义层级。标题个数、层级、列表数与代码块数均从实际稿件得出，不套用某一篇文章的固定计数。用户没有要求改标题时，不改变文章题目和各章节标题。

可以用主标题约 28px、章节约 24px、小节约 20px、正文约 16px、图注约 14px 作为排版起点，但应以稿件长度和页面效果调整。标题加粗并使用原生标题块；图注可用灰色居中。不要把所有段落都做成标题或引用块。

新字号写在外层时，内层遗留的 `font-size`、`font-weight` 或颜色样式可能仍覆盖它。修复这类冲突只调整必要的字体样式，保留文字与链接。对于“本章结果”等既有文字，直接格式化原内容；不要另拼同一前缀造成重复。

使用原生代码块恢复换行及缩进。源稿能够明确证明的弯引号误转才替换为代码需要的 ASCII 引号；字符串内部的空格、命令参数、JSON 值等都可能影响语义。不能用整篇去空白后的相等替代逐块差异核对，也不能从旧源稿覆盖用户后改的代码。

站点全局字体规则可能优先于自定义 `font-family`。必须看实际 computed style 和截图；只确认了字号、颜色或粗细时，不宣称字体族也已切换。

## 保存、失败与完成证据

在既有明确授权下完成目标原帖的保存修改或新帖发布。出现登录过期、验证码、平台拒绝或未知必填字段时，停在具体问题，不重复提交。若结果不确定，先检查同一目标的当前状态，防止重复新帖；不得把原帖修复变成另建帖子。

保存后回到正确详情页刷新，逐项验证：

- 标题与目标帖子对应；状态究竟是已发布、待审核还是草稿。
- 应有图片次数与实际图片数一致，每张均加载完成且自然宽高非零。
- 图片 URL 与本次上传映射一致，顺序正确，邻接的图注或正文符合源位置。
- 只修图片时正文与链接不应改变；排版修复时只出现授权的结构、换行及样式变化。
- 标题层级和实际视觉区别存在，正文与图注可读，代码换行完整。

如果平台刷新后丢失样式或图片，继续在原目标修复，而不是只报告编辑器里的暂存效果。最终结果说明实际验证范围与仍存在的限制，不将自动审核等待说成审核通过。
